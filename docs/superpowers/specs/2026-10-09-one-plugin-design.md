# One Figma plugin for every project — design

**Date:** 2026-10-09 · **Status:** design approved in chat, not implemented

## Problem

What the user reported:

1. Every new project needs another plugin imported into Figma.
2. Every build lands on the same Figma page.

What the code does today:

- `SKILL.md` has the scaffold (`assets/`) copied into each repo. Every copy carries its own
  `manifest.json`, all with the same name and id (`assets/manifest.json:2-3` — "Figment",
  `figment-plugin`). So each project means another *Import plugin from manifest…*, and the
  Development menu fills with identical "Figment" entries.
- The build always writes to pages named exactly `Design System` and `Screens`
  (`assets/src/03-components.js:10-24`) and to a variable collection named `Theme`.
- Building project B into a file that already holds project A destroys A:
  - B deletes A's screens (`assets/src/05-main.js:47`)
  - B overwrites A's token values (`assets/src/01-foundation.js:86`)
  - B reuses A's icons wherever the names match (`assets/src/03-components.js:27-29`), so B
    shows A's artwork with no warning
- The panel builds the moment it opens and shows only a log plus Copy/Close. You can't tell
  which project or which build is running, so a stale build goes unnoticed
  (`references/iterating.md:30`).

## Decisions

| Question | Choice |
|---|---|
| Where should builds land? | **One Figma file per project.** Each file is labelled with its project. Pages stay `Design System` + `Screens`. |
| How does one installed plugin get each project's code? | **C · one bundle with a project dropdown.** Rejected: A (only the last build is loaded), B (local server with live rebuild). |
| Should opening the plugin build straight away when the file's project is known? | **Yes**, the same one click as today. |
| Panel extras | **Rebuild button** in Figma's sidebar, and the panel **follows Figma's light/dark theme**. Rejected: clickable screen list, rebuilding only selected screens. |

## Design

### 1 · How code reaches the single plugin

```
<repo>/tools/figma-plugin/                       ~/.figment/            ($FIGMENT_HOME)
  src/*.js ─ build.sh ─▶ code.js ─┐
                                  └─ register.mjs ─▶ projects/<name>.js   one file per project
  plugin/ (manifest, ui, runner) ──────────────────▶ plugin/              ← imported into Figma once
                                                       manifest.json · ui.html
                                                       code.js = every project + runner
```

**`build.sh`** gets one new last line: `node register.mjs`.

**`register.mjs`** (new, Node, no dependencies) does five things:

1. **Name the project.** The name is `$FIGMENT_PROJECT`, or else the folder name of
   `git rev-parse --show-toplevel`. Without git it falls back to the scaffold folder's name.
   A name belongs to the scaffold folder that registered it, not to the repo. The file name is
   the name with every character outside `[A-Za-z0-9._-]` replaced by `-`.
2. **Refuse collisions.** If `projects/<file>.js` already exists and its header records a
   *different* scaffold folder, or has no readable header, exit 1 and name both folders. The
   message tells you to set `FIGMENT_PROJECT`. Otherwise two repos called `web`, or two
   scaffolds in one monorepo, would build into each other's files.
3. **Register.** Write `projects/<file>.js` as one header line followed by this project's
   `code.js`. The header is
   `// figment-project {"name":"acme","path":"/abs/scaffold","builtAt":"<ISO time>"}`.
4. **Install the shared plugin files.** Copy `plugin/manifest.json` and `plugin/ui.html` into
   `~/.figment/plugin/`. Copying the manifest also refreshes its timestamp; see *Unverified*
   for why that matters.
5. **Regenerate the bundle.** Rebuild `~/.figment/plugin/code.js` from every file in
   `projects/`, sorted by name, followed by this project's `plugin/runner.js`. Then run
   `node --check` on it:

   ```js
   // GENERATED by register.mjs from ~/.figment/projects — do not edit.
   const PROJECTS = {};
   PROJECTS["acme"] = { path: "/abs/repo", builtAt: "…", load: function () {
   …acme's code.js…
   ;return { build: build };
   } };
   …runner.js…
   ```

On the first install, `register.mjs` also prints a one-time hint: *Import once in Figma:
Plugins → Development → Import plugin from manifest… → ~/.figment/plugin/manifest.json
(Cmd+Shift+. shows hidden folders)*. Every run prints `registered acme (N projects)`.

The wrapping works like this:

- Each project's code runs inside its own function, so names like `TOKENS`, `ORDER` and
  `s1` from different projects never collide.
- Only the picked project's `load()` executes.
- The contract between a project and the runner is one function, `build()`, plus
  `figma.ui.postMessage({ type: 'log' })` for progress (the project's existing `say`).

To remove a project, delete its file in `~/.figment/projects/`. The next build of any project
drops it from the bundle.

*Limit:* every registered project ships in the one bundle. That's fine for a handful; if
opening the plugin gets slow, remove old projects from `projects/`.

### 2 · What the plugin does when opened (`plugin/runner.js`)

The runner is wrapped in its own function so its names don't leak into project code. It
owns `figma.showUI`, the message handler, the file label, the `dump` command and the
Rebuild button.

The **label** is `figma.root.getPluginData('project')`, stored inside the Figma file. All
checks run here on the main thread, not in the panel, so nothing builds over another project
without an explicit `force`.

| Opened in… | Behaviour |
|---|---|
| A file labelled with a registered project, command `build` (menu or Rebuild button) | Selects that project and **builds straight away** |
| A new file (no label, no `Screens` / `Design System` page) | Preselects the project with the newest `builtAt` and waits for **Build**. The first build labels the file |
| A file labelled `acme` when you pick `beta` | Posts `confirm` and touches nothing. The panel shows the warning; **Build beta anyway** resends with `force: true` |
| A file with no label that already has a `Screens` or `Design System` page (built before this change) | The same `confirm` warning, because it may hold another project's design |
| A file labelled `acme` when `acme` isn't registered on this machine | Status: *"This file is acme, which isn't registered here — run ./build.sh in acme."* The dropdown preselects the newest project; building it goes through the warning |
| Command `dump` | Runs `dump()` straight away in any file; no project needed |
| No projects registered | Status: *"No projects registered — run ./build.sh in a project."* |

The label is written as soon as a build is allowed to **start** (no warning was needed, or
**Build anyway** was pressed), not when it finishes. A build that fails halfway therefore stays
labelled with the project that touched it. The same step
calls `figma.root.setRelaunchData({ build: <name> })`, which puts the Rebuild button in
Figma's sidebar whenever nothing is selected.

Only one run happens at a time. A **Build** arriving while another build or dump is running
is ignored rather than started alongside it, and the panel disables its buttons while `busy`.

`dump()` moves here unchanged from `05-main.js:82-105`, because it reads the open file and
never needed project code. After a dump, the runner calls `figma.ui.resize` to make room for
the output.

Messages between the panel and the runner:

| Direction | Messages |
|---|---|
| Runner → panel | `init {projects:[{name,builtAt}], label, selected}` · `log {text}` · `busy {busy}` · `confirm {project, label}` · `label {label}` · `dump {text}` |
| Panel → runner | `build {project, force?}` · `dump` |

### 3 · The panel (`plugin/ui.html`)

```
 normal                                         wrong project picked
┌ Figment ────────────────────────────────┐    ┌ Figment ────────────────────────────────┐
│ Project [ acme          ▾ ] built 3m ago│    │ Project [ beta          ▾ ] built 1h ago│
│ This file: acme                          │    │ ⚠ This file is acme. Building beta here │
│ [ Build ]  [ Dump design system ]        │    │   replaces its screens and overwrites    │
│ ──────────────────────────────────────── │    │   its tokens.                            │
│ Building 04 settings (4 of 12)…          │    │ [ Build beta anyway ]  [ Cancel ]        │
└──────────────────────────────────────────┘    └──────────────────────────────────────────┘
```

- **Build age:** shown next to the dropdown and computed from `builtAt`. It catches a stale
  build.
- **Status line:** *This file: acme* / *New file — the first build labels it* / the not-registered
  message above.
- **Dump output:** the textarea and **Copy** appear only after a dump.
- **Close:** the custom Close button goes; Figma's own window close is enough.
- **Theme:** `figma.showUI(__html__, { …, themeColors: true })`. The panel's colours read Figma's
  CSS variables, each with a fallback, so the panel follows Figma's light/dark mode.
- **Rebuild button:** the manifest gains `"relaunchButtons": [{ "command": "build", "name": "Rebuild" }]`.
  The menu stays as two items: **Build** and **Dump this file's design system**.

Rebuild).

### 5 · Testing

`./build.sh && node test/run.cjs` stays the inner loop and still checks each project's
layout. `node register.mjs` now runs inside `build.sh`.

`test/runner.cjs` is one runnable check. It sets `FIGMENT_HOME` to a temporary folder, so it
never touches the real `~/.figment`. Steps:

1. Register the scaffold twice, as `a` and `b`, from the same repo path.
2. Load the generated `plugin/code.js` into a fresh mock.
3. Assert each of these:
   - a new file waits for a click, builds `a` when asked, and ends up labelled `a`
   - asking for `b` posts `confirm`, and the label and screens stay as they were
   - `b` with `force` builds and relabels the file to `b`
   - a fresh file with a `Screens` page and no label posts `confirm`
   - a file labelled `a`, opened with command `build`, builds without being asked
   - `register.mjs` exits non-zero when `projects/a.js` records a different repo path

### 6 · Migration

**Existing project copies:**

1. Copy in the new `build.sh`, `register.mjs`, `plugin/` and `test/`.
2. Delete the old `manifest.json` and `ui.html` from the project folder.
3. Remove the lines listed in §4 from the project's `05-main.js`.

`src/01–04` don't change.

**Figma:**

1. Remove the old per-project "Figment" entries (Plugins → Development → Manage plugins in
   development).
2. Import `~/.figment/plugin/manifest.json` once.

Existing files have Figment pages but no label, so each one shows the warning once on its
first build. Confirm, and it's labelled from then on.

## Not doing

- Live rebuild through a local server (approach B).
- A clickable screen list, or rebuilding only selected screens.
- Pages per project inside one shared file.
- Versioning the shared plugin files. Each registration copies its own `plugin/` files, so
  the last project registered wins. Add a version stamp if copies ever drift.
- Registering only builds that pass the harness. Today, too, `build.sh` writes `code.js`
  before the harness runs.

## Unverified — check in Figma desktop

These need a manual check in the Figma desktop app; the mock can't cover them.

1. **Hot reload.** Forum posts say *Plugins → Development → Hot reload plugin* watches only
   `manifest.json`. `register.mjs` copies the manifest on every build. If hot reload works,
   every `./build.sh` re-runs the plugin and rebuilds the labelled file with no click.
   Nice if true; nothing depends on it.
2. **Rebuild button in a development plugin.** The relaunch-button docs mention no
   restriction for development plugins.
3. **Theme variable names.** Check the exact Figma CSS variable names against the docs
   while implementing; the fallbacks keep the panel readable either way.
4. **Duplicate ids.** Importing a manifest whose id matches an old dev entry may be refused
   or may clash. Removing the old entries first (§6) avoids the question.

## Done when

- The only Figma setup is importing `~/.figment/plugin/manifest.json` once. A new project
  appears in the dropdown after its first `./build.sh`.
- A file labelled with one project never changes for another without **Build anyway**.
- Opening the plugin, or pressing **Rebuild**, in a labelled file builds it straight away.
- The panel follows Figma's light/dark theme.
- `./build.sh && node test/run.cjs` and `node test/runner.cjs` pass.
